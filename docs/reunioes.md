# Entregáveis por reunião

As três reuniões de acompanhamento têm objetivos diferentes, alinhados ao
que cada turma já viu de capacitação até aquele momento. A ideia não é
cobrar código pronto o tempo todo, e sim avaliar se o time está entendendo
o problema, gerenciando bem o projeto e evoluindo de forma consistente.

## 11/09 — Entrega intermediária 1: definição e estruturação

Foco principal: **"vocês entenderam o que precisam construir?"**.

**README v1**

- [ ] Descrição do projeto
- [ ] Tecnologias previstas
- [ ] Instruções iniciais para configuração do ambiente
- [ ] Integrantes e responsabilidades

**Documento de requisitos**

- [ ] Requisitos funcionais
- [ ] Requisitos não funcionais
- [ ] User stories
- [ ] Critérios de aceite
- [ ] Casos de uso, quando aplicáveis

**Backlog priorizado**

- [ ] Funcionalidades/tarefas
- [ ] Prioridade
- [ ] Responsável
- [ ] Status


**Registro do alinhamento com o cliente**

- [ ] Principais necessidades levantadas
- [ ] Decisões tomadas
- [ ] Dúvidas pendentes

**Repositório organizado**

- [ ] Branches
- [ ] Commits minimamente descritivos
- [ ] PRs sendo utilizados
- [ ] `.gitignore`
- [ ] Estrutura inicial adequada

## 05/10 — Entrega intermediária 2: marco da metade do projeto

- [ ] MVP/protótipo parcial funcional
- [ ] README v2, refletindo mudanças no projeto
- [ ] Backlog atualizado
- [ ] Funcionalidades concluídas e seus respectivos critérios de aceite
- [ ] Registro de feedback do cliente e alterações realizadas a partir dele

!!! tip "O que precisa estar feito até agora?"
    Vocês precisam ter uma versão mínima do produto (MVP) para apresentar ao cliente. Em cima disso, poderão definir o que de fato vão conseguir entregar no projeto final e conseguiremos avaliar o que vocês aprenderam nas capacitações.

## 30/10 — Reunião final: produto + documentação + legado

Nesta reunião todas as seis capacitações já aconteceram. Além dos
entregáveis específicos de cada case, existe uma **entrega de
encerramento**, comum a todos os projetos e que vai ajudar a empresa a seguir o desenvolvimento ou colocar o produto de vocês no ar.

### Banca própria do cliente

Além das entregas finais, cada grupo terá uma reunião com o cliente ou
empresa para apresentar o projeto à banca própria do cliente. Essa reunião
acontecerá uma semana antes ou depois da reunião final, conforme
disponibilidade da equipe e do cliente.

Nesses encontros, a vestimenta adequada é obrigatória: **casual
profissional**.

### 1. README final completo

Deve funcionar como porta de entrada para alguém que nunca viu o projeto:

- [ ] Contexto e solução desenvolvida
- [ ] Funcionalidades
- [ ] Tecnologias utilizadas
- [ ] Arquitetura geral
- [ ] Pré-requisitos (versões e etc.)
- [ ] Instalação e configuração
- [ ] Variáveis de ambiente (sem expor secrets!!!)
- [ ] Como executar localmente
- [ ] Estrutura do repositório
- [ ] Deploy/acesso à aplicação
- [ ] Autores

### 2. Documentação técnica

Permite avaliar principalmente as capacitações. Não deve ser um
documento gigantesco, a ideia é permitir que outra equipe assuma o
projeto no semestre seguinte.

- [ ] Visão da arquitetura
- [ ] Diagrama arquitetural/UML
- [ ] APIs utilizadas/desenvolvidas
- [ ] Modelo de dados
- [ ] Autenticação e segurança
- [ ] Estratégia de deploy
- [ ] Testes
- [ ] CI/CD

!!! tip "Sobre o uso de IA"
    Vocês podem (e devem) usar Inteligência Artificial para fazer esse relatório, bem como o README, mas garantam que o texto produzido pela IA de fato reflete o projeto de vocês e evitem repetições. Essa documentação deve ser *clara e objetiva*, diagramas são bem-vindos, e garantam que este documento só tem as informações que não podem ser lidas no próprio README do projeto ou no HANDOFF (explicaremos mais a frente sobre ele).

### 3. Backlog final

O backlog não precisa estar 100% concluído, mas deve refletir o projeto real, incluindo:

- [ ] Concluído
- [ ] Não concluído
- [ ] O que não faz mais sentido pro projeto e foi removido do escopo
- [ ] Algo que foi realocado como "Melhorias futuras"

### 4. Vídeo de demonstração

Vídeo curto, de **1 a 3 minutos**, obrigatório, mostrando pelo menos um dos casos de uso e eventuais fluxos que não tenham sido cobertos nesse caso.

!!! info "Por que gravar esse vídeo?"
    Essas evidências são muito importantes para o Code: viram material para eventos,
    divulgação, apresentação para futuros clientes, e também podem compor os portfolios de vocês, membros.

### 5. Apresentação final

Curta, de **5 a 7 minutos por equipe**, seguindo o fluxo:

Problema → Solução → Demonstração →
Aprendizados/próximos passos.

### 6. Handoff do projeto

Arquivo simples, sugerido como `HANDOFF.md`, contendo:

- [ ] O que não funciona
- [ ] Bugs conhecidos
- [ ] Pendências
- [ ] Acessos/serviços utilizados
- [ ] Orientações para continuidade/ próximos passos
